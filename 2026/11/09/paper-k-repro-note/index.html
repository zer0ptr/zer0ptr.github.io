[论文笔记]Patch-to-PoC: A Systematic Study of Agentic LLM Systems for Linux Kernel N-Day Reproduction

Title: Patch-to-PoC: A Systematic Study of Agentic LLM Systems for Linux Kernel N-Day Reproduction
Authors: Juefei Pu, Xingyu Li, Zhengchuan Liang, Jonathan Cox, Yifan Wu, Kareem Shehada, Arrdya Srivastav, Zhiyun Qian
Affiliations: University of California, Riverside
arXiv: 2602.07287 (v2, 2026-02-18)

Challenges and Motivation

N-Day 漏洞的“窗口期”来自内核生态的补丁传播延迟。上游主线修复后，补丁需要逐级向下游 stable/LTS 分支和发行版内核移植，这一过程往往耗时数十天，部分补丁甚至因遗漏而滞留超过半年。在此背景下，攻击者可以在补丁已公开但下游尚未修复的间隙分析漏洞、开发利用。因此自动化 PoC 生成具有双重意义：一是攻击方降低利用门槛，同时也促使防守方加速漏洞分诊与补丁优先级判断。

但内核 PoC 生成远比用户态困难：内核极其庞大、接口异构（ioctl、netlink 等格式差异巨大）、高度有状态且多线程，多数漏洞需要多个系统调用甚至竞态条件才能触发。该工作的出发点为检验当前 LLM 智能体是否已经跨过这个门槛。

K-Repro 系统设计

本文构建了 K-Repro —— 一个以安全补丁 commit ID 为唯一外部输入的端到端智能体系统，其工作流程为：给定补丁 commit 后让系统提取补丁内容，接着用确定性、非 LLM 流水线准备复现环境（补丁前一个 commit 的内核源码与可运行镜像），然后使用 LLM 智能体在工具集辅助下迭代分析、构造 PoC、验证崩溃，最后输出 PoC、分析报告与日志。

核心能力模块：

  • 代码浏览：定位补丁涉及的数据流与触发路径
  • 虚拟机管理：在 QEMU/KVM 环境中运行和调试内核
  • 交互：通过命令行工具与内核子系统交互
  • 调试：使用 GDB 设置断点、检查变量状态

在系统设计中存在一个关键选择：环境准备交付给确定性流水线，而 LLM 仅负责理解补丁和构造触发这个认知密集型环节，保证了实验的可复现性，同时清晰地划定了 LLM 的贡献边界。

Experiment Design and Result

数据集：来源于 Google KernelCTF 的 100 个真实可利用 Linux 内核漏洞。
模型：GPT-5.1 Codex（Medium 推理级别）与 GPT-5.1 Codex Max（XHigh 推理级别）。
整体成功率：K-Repro 在 XHigh 配置下成功复现 56/100（56%），Medium 配置下 47/100（47%），均以“生成的 PoC 触发内核崩溃”为成功标准。

口径提示：56% / 47% 是 KernelCTF 全集 100 案例口径；下文与 SyzDirect 对比的 67.1% 是可构建环境的 85 案例子集口径，两者不可混用。

成本与耗时（Table 1，全集口径）：

模型 成功率 平均成本 平均耗时 成功案例平均耗时 失败案例平均耗时
Medium 47/100 (47.0%) $4.66 33.80 min 18.67 min 47.22 min
XHigh 56/100 (56.0%) $4.02 19.33 min 11.89 min 28.81 min

从失败案例的耗时分布看，XHigh 的长尾明显更短：Medium 失败案例最长可达 299.7 min、成本 $31.3，而 XHigh 失败案例最长 70.7 min、成本 $10.9（Figure 2）。据此推测更强的模型在复杂任务中更“止损及时”，但这是笔者的解读，论文本身只报告了数字。

结论：K-Repro 的成功率显著高于 SyzDirect，且耗时从小时级压缩到分钟级。

数据集构成差异：KernelCTF 数据集中仅 3 个案例与 Syzbot 可发现的漏洞重叠。Syzbot 数据集天然排除了复杂竞态和状态累积型漏洞，这是 XHigh 在 SyzDirect 数据集上成功率（67.1%）明显高于 KernelCTF（56%）的关键原因。

Key Findings

4.1 复现并非仅单次尝试

智能体几乎不依赖单次尝试成功，而是通过多轮迭代逐步精炼 PoC。XHigh 平均每案例尝试生成 PoC 7.4 次（成功案例 4.9 次），Medium 9.1 次（成功案例 4.5 次）。一次性成功的比例不高：XHigh 10.7%、Medium 21.3%。一次性成功的案例中，XHigh 3/6、Medium 3/10 对应知识截止日期之后的补丁，说明这些成功不太可能纯靠记忆已知 PoC。

GDB 的使用模式印证了迭代特征：XHigh 在 62/100 案例中设置断点，其中 59 次断点被成功命中；即使在失败的 29 个 XHigh 案例中，断点也全部命中过。Medium 为 60/100 设断点、54 次命中，失败案例中 22 个设断点的有 18 个命中。这说明可达性通常不是瓶颈，智能体能够到达目标代码区域，失败更多发生在触发条件构造与状态控制环节。

GDB 的使用方式以变量检查为主（XHigh 平均 5.4 次/案例、Medium 4.4 次），指令级 stepping 几乎不用（全程仅 3 次）。智能体偏好在关键点观察状态，而非逐指令跟踪。

论文还发现 4 例智能体通过 GDB 直接修改执行行为（改内核内存或调用内核函数）制造“假崩溃”，此类“作弊”案例被计为失败。

4.2 子系统、漏洞类型与 commit message 的影响

子系统：按内核子系统分组，成功率差异在统计上不显著——net 的 Fisher 检验 p=1.000（XHigh）/1.000（Medium），netfilter p=0.676/0.526，bpf p=1.000/0.703。K-Repro 具有一定的泛化能力，没有严重偏科某一子系统。一个可能解释是这些子系统在野利用中被大量针对，公开文档与利用技术充足。

Table 3中表现出 K-REPRO 在竞态条件漏洞利用方面存在明显短板，造成这一现象主要取决于竞态触发需要精确的时序控制，而当前智能体的交互模式（命令行调用 + GDB 断点）对多线程时序的操控能力有限。

漏洞类型 Medium XHigh
竞态 5/24 (20.8%) 7/24 (29.2%)
非竞态 42/76 (55.3%) 49/76 (64.5%)

时序内存漏洞（UAF/DF）显著难于空间内存漏洞（OOB）。由于竞态在两类漏洞中分布不均（UAF/DF 中 26.8% 是竞态，OOB 中仅 6.3%），论文用分层分析 + Mantel-Haenszel 估计 + CMH 检验控制混杂因素：race-adjusted OR（UAF/DF vs OOB）为 0.13（p=0.002，Medium）和 0.20（p=0.023，XHigh）。即使排除竞态因素，时序内存漏洞仍统计显著地更难复现。

Commit message 的信息量（Table 5，三级分类）：

类型 说明 XHigh Medium
Type 1 不承认存在可触发问题（如仅描述代码简化） 6/13 (46.2%) 3/13 (23.1%)
Type 2 承认存在问题但不描述复现方法 44/79 (55.7%) 38/79 (48.1%)
Type 3 明确承认并给出具体触发步骤 6/8 (75.0%) 6/8 (75.0%)

信息越丰富成功率越高，但 Type 2 占绝大多数且仍有 55.7%，说明复现并不依赖直接照抄 commit message 中的复现指令。

4.3 知识截止日期：排除了依靠记忆的解释

模型知识截止日期为 2024-09-30。按补丁提交时间划分：pre-cutoff 58 例、post-cutoff 42 例。论文先验证两组的主要混杂因素分布均衡：竞态比例 24.1% vs 23.8%（OR=0.98, p=1.00），OOB 比例 15.5% vs 17.5%（OR=1.15, p=0.789）。

分组 Medium XHigh
Pre-cutoff 28/58 (48.3%) 34/58 (58.6%)
Post-cutoff 19/42 (45.2%) 22/42 (52.4%)
Fisher 检验 OR=1.13, p=0.84 OR=1.29, p=0.55

两组差异均不显著，结合 4.1 中一次性成功案例的分析，文献用统计检验排除了性能主要来自记忆公开 PoC的解释。

4.4 稳定性与收敛

第二次运行（XHigh，相同设置）：成功率 56.0% → 52.0%，平均耗时 19.33 → 22.85 min（约 18% 波动），平均成本差异 <5%。两次运行中，11 例仅首次成功、7 例仅第二次成功，至少一次成功共 63/100。

收敛性：对两次都失败的案例迭代补跑，第三次额外成功 1 例，后续不再新增。**聚合成功率收敛于 64%**。结论：单次额外重复可显著提升整体成功率，更多重复收益递减。

4.5 工具与提示词消融：成功率稳定，但执行路径改变

论文做了四组消融（提示词降级、移除 nft/tc、移除 GDB、移除 commit message），前三组对成功率的影响均不显著，但执行轨迹变化明显。

提示词降级

去掉鼓励“形成假设并验证”的高层指令后，成功率下降不显著：Medium 47.0% → 46.0%（OR=0.96, p=0.31），XHigh 56.0% → 50.0%（OR=0.79, p=0.17）。

但 GDB 使用模式剧烈变化（成功案例 vs 失败案例的断点使用次数）：

模型 基线（成功/失败） 降级后（成功/失败）
Medium 38 / 22 1 / 8
XHigh 33 / 29 5 / 16

降级后 GDB 在成功案例中几乎消失、集中到失败案例，说明调试从“验证假设”退化为“遇到困难才用”。源码浏览调用也分别减少 6.5 次/案例（Medium）和 6.0 次/案例（XHigh）。

移除子系统命令行工具（nft、tc）

成功率变化不显著：XHigh 56.0% → 46.0%（OR=0.67, p=0.20），Medium 47.0% → 50.0%（OR=1.13, p=0.78）。

但 PoC 形态完全改变：原本成功 PoC 大量依赖 nft/tc（XHigh 31/56、Medium 27/47），工具移除后几乎消失（XHigh 2/46、Medium 1/50）。成功 PoC 中 netlink/netfilter/traffic control 相关头文件的使用频率上升（Table 7），智能体转而直接在 C 代码中构造消息、调用系统调用。同时源码浏览增加（Medium +14.3 次/案例、XHigh +5.2 次/案例），VM 交互减少（Medium −10.5、XHigh −20.7）。

典型案例如 commit 317eb968：智能体最初 netlink 消息构造错误，转而用 nft 绕过；nft 不可用后，它回头阅读 nfnetlink_rcv_batch 源码，识别分发逻辑，修正 C 实现并成功触发。

移除 GDB

成功率几乎不受影响：Medium 不变，XHigh 仅降 1 个百分点。论文未发现智能体使用 kprobe/ftrace/eBPF 等替代可见性机制（这些设施在环境中被禁用）。对 10 个“用 GDB 成功”的 XHigh 案例的人工检查发现：GDB 主要用于确认 PoC 可达性或观察关键内核值，很少带来 PoC 的实质性修正——它更多是在 reaffirm 已经合理的假设，对竞态类漏洞帮助尤其有限。

移除 commit message

成功率显著下降：XHigh 39.0%、Medium 36.0%。按披露类型分层（Table 8，Δ = 无 commit message 减有 commit message，括号内为 discordant pairs b/c）：

类型 XHigh Medium
Type 1 (n=13) 0.0% (1/1) +7.7% (0/1)
Type 2 (n=79) −19.0% (19/4) −12.7% (16/6)
Type 3 (n=8) −25.0% (3/1) −25.0% (2/0)

信息越丰富的 commit message，移除后损失越大；但即使完全移除，整体成功率仍有 36%–39%，说明智能体并非依赖 commit message 才能工作。

共同启示：LLM 智能体的“成功率”对工具和提示词有一定鲁棒性，但成功路径的可解释性和效率会显著变化。工具和提示词的作用更多是引导智能体走更理性的分析路线，而非直接决定能否成功。相比之下，commit message 是唯一对成功率有实质影响的外部信号。

失败分析（第 7 节）

论文对“在所有设置下都从未成功”且有 KernelCTF writeup 的 13 个案例做了人工分析：

  • 3 例环境相关问题（如内核配置差异）
  • 2 例无法在短竞态窗口内达成竞态
  • 8 例根因分析错误或不完整（最主要、最普遍）

Case Study I（commit e26d3009）——补丁信号误导导致根因定位失败：patch 明确禁止 struct nft_set 的一条 deactivation 路径，commit message 提到“anonymous sets”。智能体据此推断漏洞是对 nft_set 的 UAF（GC 工作线程持有 stale pointer），全力复现却无法触发。人工分析表明实际 corruption 目标是另一个相关对象 struct nft_chain，但 patch 和 message 都没提。启示：补丁信号质量低甚至误导时，当前方案不足以可靠定位根因，未来需要假设多样化、外部刺激（如静态分析线索）、早期证伪循环。

Case Study II（commit 13114dc5）——忽视关键源码导致根因分析失败：触发需要内核选择队列式 crypto backend（如 cryptd）以在高并发下产生 backlog。只有“XHigh + 降级提示词”的智能体成功——因为它深入 crypto/ 子系统查找 backlog 行为，发现其依赖具体 crypto 实现，并主动强制使用队列式 backend。其他智能体只查看 include/ 下的接口级定义，未识别 crypto backend 选择这一关键控制点。启示：未来设计应引导智能体分析补丁隐含的触发链，而非依赖随机源码探索。

个人理解与启示

  1. 对自主安全智能体设计：K-Repro 的架构选择——确定性环境准备 + LLM 聚焦认知任务——是一个值得借鉴的范式。它把不可靠的环节（环境构建）与 LLM 的不确定性解耦，使得实验结果可归因。消融结果进一步说明：工具（nft/tc、GDB）对成功率影响有限，但会改变执行路径；提示词的作用是让调试行为“假设驱动”而非“被动应对”；commit message 才是唯一显著影响成功率的外部信号。这对实际部署有直接含义——在 commit message 缺失的场景（如 Android OEM 内核），预期性能会下降约 17 个百分点（XHigh 56% → 39%）。

  2. 对 N-day 攻防评估：50%+ 的复现率在分钟级、数美元成本下实现，意味着补丁公开后的自动化利用开发门槛正在实质性下降。但竞态漏洞的低成功率（20.8% / 29.2%）和时序内存漏洞的显著劣势（race-adjusted OR 0.13 / 0.20）提供了一个暂时的缓冲带——防守方至少可以在竞态类漏洞和 UAF/DF 上争取更多窗口。不过这个缓冲带能维持多久，取决于后续工作能否在时序控制上取得突破。

  3. 局限与开放问题：

    • 论文的成功标准是“触发内核崩溃”，而非实现可控利用。从崩溃到实际可利用（控制流劫持、提权）之间仍有距离，论文也承认因内核漏洞的多行为特性，难以自动验证崩溃的根因等价性（因此对 XHigh 成功案例做了人工检查，并显式排除 4 例 GDB 作弊）。
    • 竞态漏洞的瓶颈是否源于工具集限制（缺乏精确时序操控手段）还是 LLM 本身的多线程推理能力，论文未做拆解，值得进一步研究。
    • 失败分析显示 8/13 的持续失败源于根因分析错误，而根因分析高度依赖 patch 与 commit message 的信号质量——如何在低质量信号下做假设多样化与早期证伪，是下一代智能体的核心挑战。
    • SyzDirect 对比受限于其无法应用于较新内核，只能在 85 案例子集上对齐；且两数据集构成差异显著（仅 3 例重叠），对比结论应理解为“两种范式的效率画像差异”，而非严格的同分布性能排名。
